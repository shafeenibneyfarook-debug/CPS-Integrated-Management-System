# CPS Integrated Management System

## 1. Project Overview

CPS is a full-stack contractor operations and construction project management system. It supports authentication, client and supplier management, construction projects, quotations, purchase orders, shipments, invoices, inventory, import/export cost calculations, price scraping, BOQ estimation, product recommendations, dashboards, notifications, and role-based approvals.

The repository contains two application layers:

- `client/`: React 19 single-page application built with Vite.
- `server/`: Node.js and Express API using MongoDB through Mongoose.

The project can run locally as two processes, or deploy as one Vercel project. On Vercel, the React application is built as static files and the Express API is exposed through a serverless function.

## 3. Frontend Architecture

### Technology

- React 19 and React DOM.
- Vite for development and production builds.
- React Router for client-side navigation.
- Axios for API calls.
- Leaflet for map/location features.
- ESLint for code quality checks.

The frontend starts in `client/src/main.jsx`, which imports global CSS and renders `App.jsx`. `App.jsx` creates the `BrowserRouter`, wraps the application with `AuthProvider`, and registers the active routes.

### Shared frontend layout

- `client/src/layout/Layout.jsx`: authenticated workspace shell.
- `client/src/layout/Sidebar.jsx`: role-aware navigation.
- `client/src/layout/Navbar.jsx`: top navigation, user controls, and notification center.
- `client/src/layout/PublicNavbar.jsx`: public-page navigation.
- `client/src/layout/PublicFooter.jsx`: public homepage footer.
- `client/src/components/CanvasParticleBackground.jsx`: shared visual background component.

Authenticated pages are normally rendered through `AppLayout`, which combines `ProtectedRoute` with `Layout`. The admin user-management page additionally restricts access to the `admin` role.

### API client behavior

`client/src/api/axiosConfig.js` exports one Axios instance used by frontend modules.

- If `VITE_API_URL` is set, that value is used.
- During local development, the fallback is `http://localhost:5001/api`.
- In a production Vite build, the fallback is `/api`, which keeps requests on the same Vercel domain.
- A request interceptor reads `cps_token` from `localStorage` and sends it as `Authorization: Bearer <token>`.
- A `401` response clears the token and dispatches the `cps:unauthorized` browser event.

## 4. Backend Architecture

### Technology and startup

- CommonJS Node.js application.
- Express 5 HTTP server.
- Mongoose 9 MongoDB integration.
- `cors` for cross-origin requests.
- `dotenv` for local environment loading.

`server/server.js` creates the Express app, enables CORS and JSON parsing, registers all API routers, and exposes a health response at `/`. When run directly, it connects to MongoDB and listens on `process.env.PORT` or port `5000`. When imported by Vercel, it exports the Express app and does not call `app.listen()`.

### Backend module layout

Each backend module generally follows this pattern:

```text
server/modules/<module>/
|-- <module>.routes.js       Express route and role declarations
|-- <module>.controller.js   Validation, database operations, responses
`-- <module>.model.js        Mongoose schema and MongoDB model
```

Additional module-specific services/models exist where required, such as email logs, stock movements, scraped prices, price alerts, currency conversion, email delivery, and scraping services.

### Registered API prefixes

The following routers are registered in `server/server.js`:

| Prefix | Module | Responsibility |
|---|---|---|
| `/api/auth` | `auth` | Register, login, current user, profile update |
| `/api/admin` | `admin` | Admin-only user listing and status updates |
| `/api/clients` | `client` | Client records |
| `/api/suppliers` | `supplier` | Supplier records and supplier operations |
| `/api/projects` | `project` | Projects, assignments, progress, and approvals |
| `/api/shipments` | `shipment` | Shipment creation, tracking, and logistics status |
| `/api/quotations` | `quotation` | Quotations, proposal bids, revisions, and decisions |
| `/api/purchase-orders` | `purchaseOrder` | Purchase orders, approvals, supplier acceptance, receiving |
| `/api/invoices` | `invoice` | Invoices, finance verification, payments, reminders, email logs |
| `/api/inventory` | `inventory` | Inventory records and stock movements |
| `/api/import-costs` | `importCost` | Import/export landed cost and finance approval |
| `/api/price-scraper` | `priceScraper` | Scraped prices and admin verification/inventory sync |
| `/api/boq-estimator` | `boqEstimator` | BOQ estimate generation and persistence |
| `/api/product-recommendations` | `productRecommendation` | Product recommendations and price alerts |
| `/api/dashboard` | `dashboard` | Dashboard statistics and recent activities |

All prefixes except `/api/auth` and `/api/admin` are mounted with the global `authenticate` middleware in `server/server.js`. Individual routers may apply `authenticate` again and use `authorize(...)` for role-specific actions. The admin router applies both authentication and the `admin` role check to all of its routes.

### Authentication and authorization flow

1. A user registers through `POST /api/auth/register` or signs in through `POST /api/auth/login`.
2. The server validates the account, hashes passwords using Node.js `crypto.scrypt`, and returns a signed token.
3. The frontend stores the token as `cps_token` and Axios sends it with later requests.
4. `server/middleware/auth.js` verifies the HMAC token, loads the user from MongoDB, checks `isActive`, and attaches the user to `req.user`.
5. `authorize(...roles)` checks `req.user.role` for restricted operations and returns `403` when the role is not allowed.

Supported roles defined during registration are `admin`, `manager`, `operations_officer`, `staff`, `accounts_officer`, `client`, and `supplier`. The first registered user is assigned the administrator role; later registrations default to the client role unless a valid role is supplied.

The JWT secret is read from `JWT_SECRET`. The code contains a development fallback, but production must always define a strong `JWT_SECRET` in Vercel. Changing the secret invalidates existing tokens.

## 5. Database and External Services

- `server/config/db.js` reads `MONGO_URI` and connects to MongoDB/MongoDB Atlas through Mongoose.
- `server/config/groqService.js` reads `GROQ_API_KEY` and optionally `GROQ_MODEL` for AI-assisted BOQ estimation.
- `server/modules/priceScraper/scraperService.js` reads `FIRECRAWL_API_KEY` for live price scraping.
- `server/modules/invoice/emailService.js` handles invoice-related email delivery; configure any provider-specific variables required by that service before enabling email in production.

Never commit `server/.env` or any other `.env` file. Use Vercel Environment Variables for deployed secrets.

## 6. Vercel Deployment Architecture

### Files used by Vercel

```text
CPS_Full/
|-- api/
|   `-- index.js       Imports the Express app and connects to MongoDB once per warm function
|-- client/
|   |-- src/            React source code
|   `-- dist/           Generated Vite output after the build
|-- server/
|   |-- server.js       Exportable Express app and local server startup
|   `-- ...              Controllers, routes, models, middleware, and services
`-- vercel.json         Build command, output directory, and rewrites
```

`api/index.js` is the Vercel function entrypoint. It imports the Express app from `server/server.js`, caches the MongoDB connection promise during a warm function instance, and forwards each request to Express.

`server/server.js` uses this guard:

```js
if (require.main === module) {
	startServer();
}

module.exports = app;
```

This means local execution starts an HTTP listener, while Vercel can import the app without starting a second listener.

### `vercel.json` behavior

The root `vercel.json` contains:

- `installCommand`: installs dependencies in both `client/` and `server/`.
- `buildCommand`: runs `npm run build --prefix client`.
- `outputDirectory`: publishes `client/dist` as the static frontend.
- API rewrite: `/api/:path*` is sent to `/api`, which resolves to `api/index.js`.
- SPA rewrite: other browser paths are sent to `/index.html`, allowing React Router to load on direct navigation or page refresh.

The Vercel project root must be the repository root containing `vercel.json`, `api/`, `client/`, and `server/`. Do not set Vercel's Root Directory to `client/`, or the serverless API and root deployment configuration will not be available.

### Vercel request flow

```text
Browser request
	|
	|-- /api/auth/login or /api/projects
	|       -> vercel.json API rewrite
	|       -> api/index.js
	|       -> server/server.js Express app
	|       -> route, middleware, controller, MongoDB
	|
	`-- /, /dashboard, /projects/123, etc.
			-> client/dist static files or index.html SPA fallback
			-> React Router renders the page
```

Because the frontend uses `/api` in production by default, `VITE_API_URL` is optional when the frontend and backend are deployed together in this Vercel project. Set it only when the API is hosted at a separate domain, for example `https://api.example.com/api`.

## 7. Required Environment Variables

Configure these in Vercel Project Settings -> Environment Variables for Production, Preview, and Development as appropriate:

| Variable | Required | Purpose |
|---|---|---|
| `MONGO_URI` | Yes | MongoDB connection string |
| `JWT_SECRET` | Yes | Production token signing secret |
| `GROQ_API_KEY` | Optional | Groq AI features for BOQ estimation |
| `GROQ_MODEL` | Optional | Override the preferred Groq model |
| `FIRECRAWL_API_KEY` | Optional | Live price scraping |
| `VITE_API_URL` | Optional | Separate API base URL; defaults to `/api` in production |
| `PORT` | No for Vercel | Local server port; Vercel supplies its own runtime |

For local development, place server variables in `server/.env`. The local server currently uses port `5001` when configured in `.env`; the client development fallback also points to `http://localhost:5001/api`.

## 8. Local Development

From the repository root:

```bash
npm install
npm install --prefix client
npm install --prefix server
npm run dev
```

The root development script starts both applications through `concurrently`. Alternatively:

```bash
cd server
npm start

cd client
npm run dev
```

Useful client checks:

```bash
npm run lint --prefix client
npm run build --prefix client
```

The server package currently has no automated test suite; its test script is a placeholder.

## 9. Deployment Checklist

1. Push the repository branch to GitHub and import the repository into Vercel.
2. Select the repository root as the Vercel Root Directory.
3. Confirm Vercel detects `vercel.json`.
4. Add `MONGO_URI` and a unique strong `JWT_SECRET`.
5. Add `GROQ_API_KEY` and `FIRECRAWL_API_KEY` if those features are required.
6. Deploy and open the generated Vercel URL.
7. Test `/`, `/login`, a protected page refresh such as `/dashboard`, and an API health request.
8. Confirm MongoDB Atlas allows connections from the deployed environment and that the database user has the required permissions.

## 10. Security Notes

- Do not commit `.env`, database connection strings, API keys, or JWT secrets.
- Rotate any credential that has been exposed in source control, documentation, logs, or chat.
- Use a different strong secret for each environment when possible.
- Keep production CORS restrictions and email provider settings under review before public launch.
- The API depends on MongoDB being reachable from the Vercel runtime; a successful frontend build does not prove database connectivity.
